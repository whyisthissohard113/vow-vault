## Query-path analysis (the four Phase 13 paths)

1. **Sweep** — `weddings JOIN expiry_rules ON wedding_id` filtered `status IN (active, upload_closed, download_only, expired, archived) AND deleted_at IS NULL`.
   **Fine, no change.** `weddings_status_idx (status)` drives the IN-filter (the `deleted` tombstone value is not in the list, so tombstones are excluded at the index); `expiry_rules_wedding_id_unique_idx (wedding_id)` is the ideal inner-join lookup; the sweep's LEFT JOIN to vaults uses `vaults_wedding_idx (wedding_id)`. `deleted_at IS NULL` is a cheap residual filter. A partial `(status, deleted_at) WHERE deleted_at IS NULL` composite would only shave heap lookups on soft-deleted rows that are already excluded by the status IN-list — not worth the extra index/write amplification.

2. **Guest session revocation** — `UPDATE guest_sessions SET status='revoked' WHERE vault_id IN (…) AND status='active'`.
   **Indexed.** The new `guest_sessions_vault_status_idx (vault_id, status)` serves exactly this predicate as an index scan (vault_id range + status residual without heap fetch). The old `(vault_id)` index served the range but required a heap probe + status filter on every candidate row; it was removed as redundant — the composite's `vault_id` prefix covers every vault_id-only query, including the purge path below.

3. **Purge** — every FK-column lookup in `purgeWedding` is already backed:
   | Query | Supporting index (existing) |
   |---|---|
   | `media WHERE wedding_id` | `media_wedding_idx` |
   | `media_variants WHERE media_id IN` | `media_variants_media_idx` (+ `media_variants_media_type_unique_idx` prefix) |
   | `media_processing_jobs WHERE media_id IN` | `media_processing_jobs_media_idx` |
   | `memories WHERE wedding_id` | `memories_wedding_idx` (already present from 0000) |
   | `slideshows WHERE wedding_id` | `slideshows_wedding_idx` |
   | `slideshow_items WHERE slideshow_id IN` | `slideshow_items_slideshow_order_idx` (prefix) |
   | `flipbooks WHERE wedding_id` | `flipbooks_wedding_idx` |
   | `flipbook_pages WHERE flipbook_id IN` | `flipbook_pages_flipbook_page_number_unique_idx` (prefix) |
   | `qr_codes WHERE wedding_id` | `qr_codes_wedding_idx` |
   | `vaults WHERE wedding_id` | `vaults_wedding_idx` |
   | `guest_sessions WHERE vault_id IN` | `guest_sessions_vault_status_idx` (new, prefix) |
   | `vault_access WHERE vault_id IN` | `vault_access_vault_user_unique_idx` (prefix) |
   | PK deletes (media, slideshows, flipbooks, vaults, weddings) | primary key lookups |
   **No additional purge index added** — nothing was missing.

4. **Deadline recalc / package resolution** (`recalculateWeddingDeadlines`, `resolveWeddingPackageCode`) — `expiry_rules_wedding_id_unique_idx` and PK lookups cover them.

**Verdict: none of the four hot paths lacks a supporting index after 0003.**

## Risks / notes for the next worker

- The migration is idempotent-friendly (DROP INDEX IF EXISTS / CREATE INDEX IF NOT EXISTS) and can be re-applied safely.
- Keeping BOTH the old `vault_id` index and the new composite would have been pure write-amplification for zero read benefit; the composite's prefix serves all `vault_id`-filtered reads in the engine. If any external ops tooling referenced `guest_sessions_vault_idx` by name, it must switch to `guest_sessions_vault_status_idx`.
- The `guest_sessions_status_expires_idx (status, expires_at)` index is retained for expiry/cleanup scans of sessions (non-lifecycle hot path).
